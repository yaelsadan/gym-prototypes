v21 — matkot transition: ball stroke + animation fix

The glitch, and what it actually was

  • The matkot animation is a Lottie whose ball and paddles are image layers (ty: 2), 180 frames at 30fps — a 6-second loop.
  • render() rebuilds frame.innerHTML, which throws away the #matkot-lottie node, so mountLottie() had to destroy() and loadAnimation() again — from frame 0.
  • Since v17, roomTick() called render() every second while the student sat on the waiting screen. So the 6-second loop was restarted once a second and never got past its first beat. That is the “scratched disc”.
  • Fixed at the state level: the room clock now calls syncRoomUI(), which writes the two DOM nodes that actually show the room time (the header pill’s text node and .wait-num) and nothing else. Zero re-renders on a tick.
  • Belt and braces: mountLottie() is now idempotent (mounting on the same node twice is a no-op, so two instances can never fight over one element) and playhead-preserving — a genuine scene change resumes from the frame we left on. The playhead only resets when we leave every transition screen.

The ball, and the two waiting states

  • Ball stroke: the image_0 asset is regenerated — same 231×231 canvas, same baked yellow, same outer radius (94.5), with a 12px charcoal ring drawn inside the edge. That renders as a 1.78px charcoal stroke on a 28px ball, so the ball reads clearly over the white paddles. The ball’s size does not change and the paddle artwork is untouched.
  • State A — room still active (consent decline · own camera/mic off → leave room · Leave room · report submit/skip): the synchronised countdown, straight from ST.roomLeft, ticking down, with the same yellow emphasis in the final 10 seconds. At 00:00 it routes back to the Main Room.
  • State B — time’s up (roomLeft === 0): roomEnd() and backToMain() both route to the return transition, which carries “Time’s up - heading back to class” and no countdown. The waiting variant can no longer render a 00:00 countdown.
  • The loader survives only as a debug fallback, for the state where no room clock is running at all.

Open: the ball’s baked fill is #FEE300, not the #F9E24C brand token. I left it exactly as it was, because this pass was scoped to the stroke — say the word and I will repaint it to the token in the same asset.

v16 — presentation-mode timer fix (surgical)

  • What it actually was. The geometry was innocent. A cascade resolver over the full stylesheet returned identical values in both modes for every timer property — stroke-width: 5, stroke-linecap: round, stroke-dasharray: 175.93, radii 30.9 / 28 / 25.25, balls r 3.4, balls painted last. The single resolved difference was the disc’s width/height.
  • The real cause: rasterisation. Four filter: drop-shadow() rules sat on the timer — .demo-timer (from v1), .tile-timer (v12), the leading ball (v14) and the warning state (v14). A CSS filter pushes the element and its subtree into an offscreen raster buffer. In presentation the frame becomes 100vw × 100vh and the stage composites at a different layer scale, so those buffers rasterise coarser. The first things to disappear are exactly the sub-pixel parts of the timer: the 0.5-unit rim/face hairlines and the 0.72-unit charcoal ball outline. With the outline gone, the arc’s round cap reads as a naked, flat edge — the reported symptom.
  • The fix: zero filters in the timer. Disc separation and the coral warning glow are now box-shadow on the circular (border-radius: 50%) disc — pure vector, resolution-independent, crisp at any size. filter: none is asserted on the disc, the ring, both balls and both containers.
  • One construction, one token. Presentation now differs by exactly one custom property: --d, the disc diameter (152/128 regular, 178/148 in presentation). Width, height, number size (calc(var(--d) * .41), .49 for single digits) and letter-spacing (-.022em) all derive from it. There is one declaration of every stroke width, cap, radius and colour, shared by both modes. No separate presentation timer, no simplified fallback.
  • Validated in both modes by rendering the timer at its real pixel sizes — 152 / 128 (regular) and 178 / 148 (presentation) — and running the same pixel proof at four progress values in each: zero yellow past the leading ball, zero breaks in either ball’s charcoal outline, stream continuous between the balls.
  • Untouched: header room timer (flat text, yellow only in the final 10s), Done badge, the single Done sparkle, the Carousel cue, and every behavior — routing, timing, TIP, camera/mic, report, waiting, Solo.

v04 timer model

Room timer (always present)

  • Small top-bar pill = time remaining in the room.
  • Normal = neutral pill.
  • Final 10s = Citizen branded yellow attention state — “ending soon”, not alarm.
  • No separate final-3s red/emergency state.

Activity timer (activity-specific)

  • Not a default element — appears only when the activity needs a countdown.
  • Generic timed round: one central countdown on the seam between tiles, slightly lower, a touch more dominant.
  • Operation Grandma: timer attaches to the active speaker’s tile (follows whose turn it is), tying it to turn-taking rather than a global room countdown.

Visual language: branded yellow for attention / time-ending; no amber/orange + red combination; no full red fills for timers (red is reserved for true error/blocking states).

How to read the demo

  • Activity = None → only the small Room pill (a plain room with no timed mechanic).
  • Activity = Timed round → central Activity timer + Room pill.
  • Activity = Operation Grandma → the Activity timer sits on the active speaker’s tile; switch Active speaker (You / Dana) to move it.
  • Room timer = Final 10s → the top pill turns branded yellow regardless of activity.
